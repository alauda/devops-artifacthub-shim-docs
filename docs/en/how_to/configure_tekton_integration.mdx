# Configure Tekton Integration

## Feature Overview

`artifacthub-shim` serves Tekton catalog resources through Artifact
Hub-compatible APIs. Tekton hub resolver and Pipelines as Code should use the
in-cluster shim Service, not public `artifacthub.io` or `api.hub.tekton.dev`.

Artifact Hub Shim `v1.0.0` currently works out of the box with the released
`Alauda Container Platform Pipelines` `v4.14.0`. The minimum versions for the `4.10`,
`4.6`, and `4.0` lines are `v4.10.2`, `v4.6.4`, and `v4.0.17` after those
patches are released. Standard installations with Alauda Container Platform
Pipelines 4.14 use these
defaults:

| Setting | Value |
| --- | --- |
| Shim namespace | `artifacthub-shim-system` |
| Shim Service | `artifacthub-shim-api` |
| Resolver Artifact Hub API | `http://artifacthub-shim-api.artifacthub-shim-system.svc.cluster.local/` |
| PAC Hub URL | `http://artifacthub-shim-api.artifacthub-shim-system.svc.cluster.local` |
| Task catalog | `catalog` |
| Pipeline catalog | `catalog-pipelines` |

## Tekton Hub Resolver

When the plugin uses the standard namespace and release name, Alauda Container
Platform Pipelines 4.14 sets the resolver defaults during component
installation. The same Service URL
applies after the minimum `tektoncd-operator` patch versions on the `4.10`,
`4.6`, and `4.0` lines are released. For custom installations, merge this
configuration into `TektonConfig.spec.pipeline`:

```yaml
enable-hub-resolver: true
hub-resolver-config:
  artifact-hub-api: http://artifacthub-shim-api.artifacthub-shim-system.svc.cluster.local/
  default-artifact-hub-task-catalog: catalog
  default-artifact-hub-pipeline-catalog: catalog-pipelines
  default-kind: task
  default-tekton-hub-catalog: catalog
  default-type: artifact
```

`default-tekton-hub-catalog` must stay present even when `default-type` is
`artifact`; current resolver versions still read it while preparing defaults.

If `artifacthub-shim` is installed into another namespace, replace
`artifacthub-shim-system` in `artifact-hub-api` with the install namespace.
If the Helm release name changes and the Service name is overridden, update the
Service host as well.

### Resolver defaults for run details

The enhancement capabilities endpoint exposes the resolver defaults that a DevOps
UI run-detail consumer may need when historical metadata omits a Hub parameter:

```http
GET /apis/v1alpha1/capabilities
```

Use the route for the cluster that will execute the run. The same endpoint is
available through the global-cluster gateway at
`/tektoncd-enhancement/apis/v1alpha1/capabilities` and through the
cluster-rewrite route at
`/clusters-rewrite/<cluster>/tektoncd-enhancement/apis/v1alpha1/capabilities`.
All routes require a Bearer token. The enhancement service reads
`TektonConfig/config.spec.targetNamespace` on every request and loads
`hubresolver-config` from that target namespace. If target-namespace discovery
is unavailable, it uses the enhancement Pod's `SYSTEM_NAMESPACE`; a missing
ConfigMap then permits the legacy `${SYSTEM_NAMESPACE}-resolvers` lookup.

The response may contain `hubResolverDefaults.defaultType`,
`defaultKind`, `defaultArtifactHubTaskCatalog`,
`defaultArtifactHubPipelineCatalog`, and `defaultTektonHubCatalog`. A consumer
fills only omitted `resolver=hub` parameters in a copy of the query: explicit
values, including an explicit empty string, remain unchanged; `defaultType`
and `defaultKind` are used before selecting a catalog. Task and Pipeline
Artifact Hub lookups use their corresponding catalog fields. An Artifact Hub
StepAction has no default catalog and must supply one explicitly; Tekton Hub
references use `defaultTektonHubCatalog` for any resource kind. The saved
PipelineRun or TaskRun spec remains the execution source of truth.

The endpoint is optional for compatibility with older enhancement backends. On
`401`, `403`, `404`, `5xx`, timeout, or gateway/network failure, keep the
original run metadata and do not send a package, version, raw-manifest, or
batch-item request with an undefined or guessed catalog. Collection list
requests do not require a catalog. The service reads the ConfigMap on each
capabilities request, so changes become visible after the next request without
a restart.

## Pipelines as Code

PAC remote annotations use PAC settings, not `TektonConfig` resolver settings.
For custom installations, set these PAC settings on the
`OpenShiftPipelinesAsCode` resource or the reconciled PAC configuration source:

```yaml
hub-url: http://artifacthub-shim-api.artifacthub-shim-system.svc.cluster.local
hub-catalog-type: artifacthub
hub-catalog-name: catalog
```

Do not append `/api/v1` to `hub-url`; PAC adds it for Artifact Hub providers.
Keep `hub-catalog-type: artifacthub` so PAC does not probe `/api/v1/stats` and
fall back to Tekton Hub behavior.

PAC has one default `hub-catalog-name`. It therefore asks shim for remote
Pipeline annotations from `catalog`; shim falls back to `catalog-pipelines` for
Pipeline detail lookups. New explicit hub resolver references should still use
`catalog-pipelines` for Pipelines.

## DevOps Hub UI

The DevOps UI keeps the stable `/hub` gateway path. The chart renders a
dedicated `hubIngress` that rewrites `/hub(/|$)(.*)` to the canonical shim API.
The shim API itself does not register `/hub/**` handlers.
